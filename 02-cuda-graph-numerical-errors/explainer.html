CUDA graph replay pitfalls

A CUDA graph is a recording. Replaying it re-issues the GPU work captured once, with the same kernel arguments, the same launch shapes and the same memory addresses, and nothing else. Every example on NVIDIA's numerical-errors troubleshooting page follows from that rule. Below, each one is shown buggy and fixed, with the values it actually produced and what happens underneath.

The one rule

What a graph records

Inside with torch.cuda.graph(g): PyTorch puts a side stream into capture mode. Your Python runs normally, but every kernel launch, memcpy and memset sent to that stream is not executed. It is appended to the graph as a node instead. A kernel node stores the function, its launch shape and a copy of its argument bytes. Tensors allocated during capture come from a memory pool owned by the graph, so their addresses stay valid between replays. g.replay() then enqueues the whole node list with one call.

Replay re-issues

  • every captured kernel, with its saved argument bytes (pointers and scalars)
  • captured memcpy and memset nodes, with their saved addresses
  • the same launch shapes

Replay never re-runs

  • Python: branches, loops, counters, prints, hooks
  • allocations and frees
  • host syncs such as .item() (illegal inside capture)
  • work sent to any stream that is not part of the capture

And capture itself computes nothing

  • Values produced inside the with block exist only after the first replay. That is why every example below replays once right after capturing.

Frozen choice

Decisions made on the CPU

Anything Python decides while capturing becomes a constant of the graph: which branch, which scalar, how many elements, what the host-side state was. The fix is always one of two moves. Either turn the decision into data the GPU reads at replay time, or keep it outside the graph.

Dynamic control flow

A Python if on a runtime value picks one branch at capture. Every replay repeats that branch.

Bug, measured. Same as the page.

All four fixes (torch.where, a branching CUDA kernel, two graphs chosen on the CPU, partial capture) gave the same correct strip.

Underneath
  • idx % 2 is evaluated by Python, once, at capture. The graph holds a subtract node and a multiply node, and idx is not an argument of either.
  • torch.where works because the condition becomes a tensor. The select kernel reads it through a pointer at replay time, so fill_(i) before each replay changes the result. The cost is that both branches always run.
  • The custom kernel reads idx[0] from device memory and branches per thread, so only one path does work. It must be launched on getCurrentCUDAStream(), otherwise it is not captured (see library streams). It compiled with load_inline for sm_121 and ran correctly.
  • Two graphs (one per branch) and partial capture (branch in eager code, then a graph for the static rest) keep the decision on the CPU, outside the recording.
  • CUDA 12.4 added conditional graph nodes, but the page notes that PyTorch's graph API does not expose them yet.

Capture-aware code

Code that asks is_current_stream_capturing() and computes something different gets that different computation baked into every replay.

Bug, measured (y.fill_(i) each iteration). Same as the page.

Underneath

The check returns True during exactly one execution of the Python: the capture. The negation kernel is recorded, and at replay time the check does not run at all, so it cannot "switch back". Changing how the same result is computed is fine. Both fixes printed 0..5.

cases: capture-aware/bug · fix · fix-sleep

Python scalars become constants

A Python number passed to an op becomes a kernel argument. Its capture-time value is copied into the graph node.

Bug, measured (2i). Same as the page.

Underneath
  • A kernel node stores a copy of the launch's argument bytes. A Python scalar is passed by value into those bytes: 3 is in the node itself.
  • A tensor is passed as a pointer. The kernel loads whatever is at that address when it runs, so fill_ between replays changes the result.
  • Constants that never change (a dropout rate, a hidden size) are safe as Python values. Anything computed per step is not.

cases: dynamic-scalar/bug · fix

Hidden scalars: learning rate, step counter, GradScaler, RNG

The page warns about scalars that hide inside training loops. Each fragment was made runnable.

Learning-rate bug, measured: w after each step, with grad = 1.

Underneath
  • Step counter. Same mechanism: model(x, step=global_step) froze the step at its capture value. A step tensor updated with fill_ fixed it.
  • GradScaler. The loss scale is already a device tensor (scaler._scale). scale(loss) multiplies by it through a pointer, and update() rewrites it in place. So capturing forward plus scaler.scale(loss).backward() and calling step() and update() in eager code is safe. With the scale doubling every step, the weights and scale matched an eager run exactly. The page's ❌ variant puts step() inside the graph. That does not fail silently: step() checks found_inf on the host, a cuStreamSynchronize, and capture aborts with operation not permitted when stream is capturing.
  • RNG. A random kernel in a graph reads its seed and offset through device pointers. PyTorch's generator header describes how each replay first advances that offset by the graph's total consumption. So 5 replays of a captured dropout gave 5 different masks. On torch 2.14 this also held for a custom torch.Generator that was never passed to register_generator_state. The generator creates per-capture state on first use.

Dynamic shapes

Launch shapes are fixed at capture. A graph captured for 4 elements processes 4 elements, always.

Bug, measured: the 8 requested outputs. Same as the page.

Underneath

The grid size and the element count are part of the recorded launch, and the input and output buffers were allocated for 4 elements. There is nowhere to put element 5. Padding to one maximum wastes compute on zeros. Bucketing captures one graph per size class: sizes 3, 8 and 5 ran through buckets 4, 8 and 8 and came out correct. vLLM does the same per padded batch size. In topic 01, Step C, that came to 2995 graph instantiations.

cases: dynamic-shape/bug · fix-pad · fix-bucket

Host-side state mutated inside the graph

A counter incremented inside the captured function increments during capture only. Eager code after the graph then reads a frozen value.

Bug, measured: y after eager_func. The state reads 1, 2, 3, 4, 4, 4 instead of 1..6. Same as the page.

Underneath

state[0] += 1 is a CPU instruction. It never becomes a node. The same applies to list.append, dictionary updates and self.step = i. If code outside the graph depends on the value, either mutate it outside, or make it a tensor that a captured kernel updates.

cases: host-state/bug · fix-outside · fix-gpu-tensor

Frozen pointers

Addresses

A graph doesn't know about Python variables or tensor objects, only raw addresses. Anything that changes what lives at an address breaks it silently: rebinding a name, freeing a tensor, reusing a buffer across replays, two graphs handed the same block.

Reassigned inputs

Rebinding a Python name to a new tensor moves the name. The graph keeps reading the old address.

Bug, measured. Same as the page.

What the name and the graph point at, at i = 4
block A
lr from i=1 · value 1 · freed at i=2← the graph's mul node reads here
block B
lr from i=4 · value 4← the Python name lr now points here
Underneath

Block A is freed at i = 2, the moment the name moves on. This run still read 1 only because the caching allocator happened to hand other free blocks to the later tensors. Once A is recycled, the graph reads someone else's data (next example). Watch for hidden inputs that cross the graph boundary: globals, preprocessing outputs, module attributes and caches.

cases: dynamic-input/bug · fix

The autocast weight cache

Under autocast, the FP16 copy of a weight is cached. A graph that uses the cached copy never sees the weight change.

Bug, measured. Same as the page.

Underneath

Autocast caches the casted copy of a leaf tensor that requires grad, for as long as the autocast context lives. In the bug, the warmup filled the cache. The captured matmul therefore reads the cached FP16 buffer, and no cast kernel is recorded. Writing new values into w never reaches that buffer. After the context exits, the cache entry is dropped, so its memory can also be recycled under the graph. With the cache disabled, or with autocast entered inside the capture, the cast is a node, and replay re-casts w each time.

On torch 2.14

Option 2 as printed on the page has no warmup. In a fresh process its matmul is the first one, so cuBLAS creates its handle inside the capture, and capture fails with CUBLAS_STATUS_NOT_INITIALIZED. One eager matmul first, the usual "warm up before capture" rule, fixes it.

cases: autocast-cache/bug · fix-no-cache · fix-inside

Freed inputs

When the last Python reference to a graph input goes away, the caching allocator gives its block to the next request of that size.

Bug, measured: the 4 output elements.

Addresses from the run
0x32ee00000
static_input (freed on return)other_tensor = randn(4)← the graph's mul node still reads here

The output is 2 × randn: the replay doubled whatever other_tensor holds.

On torch 2.14: the CPU-tensor variant

The page's second example frees a CPU tensor whose H2D copy was captured (torch.tensor(i).to("cuda", non_blocking=True)). On torch 2.14 the copy is refused at capture: Cannot copy between CPU and CUDA tensors during CUDA graph capture unless the CPU tensor is pinned. Both of the page's fixes fail the same way, including torch.tensor(i, device="cuda"), which is itself a pageable copy. A graph-safe replacement is torch.full((), i, device="cuda"), a fill kernel.

We rebuilt the bug with pinned memory, and it still did not reproduce. After capture, new pinned tensors landed at 0x32ee00200, never at the captured block 0x32ee00000. In eager mode the same allocator does reuse a freed pinned block once its copy has finished. So PyTorch now withholds host blocks used by a capture.

Output tensor reuse

A graph's output is one buffer that every replay overwrites. Appending it to a list appends the same buffer three times.

Bug, measured. Same as the page.

Underneath

In eager mode, each forward pass allocates a fresh output, so keeping references is safe. In a graph, the output was allocated once, in the graph's pool, and its address is part of the recording. This matters for accumulating predictions, metrics, gradient accumulation and pipeline stages. It also matters across graphs that share a pool: another graph's replay can overwrite your output too (next example).

cases: output-reuse/bug · fix

Graphs sharing a memory pool

With pool=graph1.pool(), graph 2 is allocated as if it runs after graph 1. Replaying in another order lets graph 1's scratch memory land on graph 2's output.

Bug, measured. Same as the page, and all three fixes gave 8 and 4.

The shared pool, with addresses printed during capture
0x327e00000
graph 1: t1 (scratch, freed at end of capture)graph 2: y2 (output)
0x327e00200
graph 1: y1 (output)
  1. graph2.replay() writes y2 = 4 into 0x327e00000.
  2. graph1.replay() writes t1 = 1 × 3 = 3 into 0x327e00000, then y1 = 8.
  3. Reading y2 now gives 3.
Underneath

During capture the pool behaves like the normal caching allocator. When graph 1's capture ends, t1 has no Python reference, so its block goes back to the pool's free list, and graph 2's capture is handed that block for y2. That assignment is correct only if graph 1 always finishes before graph 2 runs. The page's rule of thumb: when sharing a pool, replay in capture order, and never concurrently.

A bug this harness made itself

The first version of the "read immediately" fix printed 17 instead of 8. The helper that built the graphs created x1 locally and didn't return it, so x1 (at 0x32ee00000) was freed. The y2.clone() was handed that block and wrote 4 into it. graph1 then computed 4 × 3 + 5 = 17. That is exactly the freed-input bug, made by accident in code written to show a different one. The other shared-pool cases allocated nothing in between, so they looked fine.

Replay order with make_graphed_callables

Graphing several callables at once makes six graphs (a forward and a backward each) in one pool. Interleaving them the way pipeline parallelism does corrupts gradients.

Bug, measured gradients for x = 1, 2, 3. Same as the page.

Underneath

The pool's addresses were assigned by simulating execution in capture order: a buffer that is dead after one graph is handed to the next. Saved activations that a backward graph needs are only guaranteed intact if the graphs in between are the ones the capture assumed. The source comment in make_graphed_callables says it captures "fwd 1, fwd 2, ... fwd N, then bwd N, bwd N-1, ... bwd 1". Its docstring says the tuple order must be the order the callables run in the live workload.

On torch 2.14

The page's fix 1 (y0.backward() right after f0, and so on) assumes alternating capture. It is itself a mismatch and produced the same wrong gradients as the bug. Its other two fixes (separate pools, or capturing manually in replay order) work.

Missing nodes

Which work was recorded

Capture is per stream. Work on the capturing stream, or on a stream joined to it through events, becomes nodes. Work sent anywhere else executes once, immediately, and is gone from every replay. Python that dispatches the work, like a submodule's forward and its hooks, is not part of the graph either.

A library that launches on the default stream

A library that hard-codes the default stream works in eager mode. Under capture, its kernel is never recorded.

Bug, measured: y = (i + 1) × 2. Same as the page.

Underneath
  • torch.cuda.graph captures on a side stream. x + 1 goes there and becomes a node writing into the graph pool. It has not executed.
  • x * 2 goes to the default stream and executes right away. It reads the pool buffer that x + 1 will only fill at replay time. In this run that buffer held 0, so the result was 0, written into an ordinary tensor. The Python name y now points at that tensor, and no replay ever writes it.
  • No error was raised in this run, so the only symptom is the wrong value.
  • Option B works because wait_stream records an event on the capturing stream and makes the internal stream wait on it. That pulls the internal stream into the same capture. The join at the end is required before capture can end. This is how multi-stream work, such as the overlap patterns from topic 01, ends up inside one graph.
  • The page's diagnosis tool is a profiler timeline that shows which stream each kernel ran on. That is what 01-cuda-streams/nsys_streams.py reports.

cases: library-stream/bug · fix-current-stream · fix-pass-stream · fix-internal-stream

Module hooks that never fire

After make_graphed_callables, only the top module's hooks run. The submodules' forward is never called.

Bug, measured. Same as the page.

Underneath

Hooks are dispatched by Module.__call__. make_graphed_callables replaces the top module's forward with a function that replays the graph, so the top module's __call__ still runs (and its hook fires), but nothing ever calls the three submodules. Logging, activation caching or gradient tweaks done in per-layer hooks silently stop. Either capture at a finer granularity with CUDAGraph, or move that logic outside the graphed region.

cases: module-hooks/bug · workaround-top-level

Async replay

Replay is asynchronous

graph.replay() returns as soon as the work is queued. Anything the CPU, or another stream, does to the graph's memory afterwards races the queued work. These two examples belong to the CUDA streams topic as much as to graphs.

Writing pinned memory the GPU has not read yet

The graph's H2D copy reads a pinned host buffer. The CPU loop rewrites that buffer long before the queued copy gets to it.

Graph bug, measured (x²). Same as the page.

Eager version on a side stream, measured. Same as the page: not a graph-only bug.

Underneath
  • A non_blocking copy from pinned memory is a DMA that reads the host buffer when the copy engine gets to it, not when you call it. The graph recorded that host address.
  • replay() and clone() only enqueue, so the CPU finishes its four iterations while the GPU is still in the first 50 ms sleep. Every copy then reads 3, and every output is 9.
  • An event recorded after the replay and synchronized before the next write lets the CPU wait for exactly the work that reads the buffer, without draining the whole device. All three fixes gave 0, 1, 4, 9.
  • x_cuda.copy_(x_cpu) is safe for a different reason. A blocking copy from pinned memory makes the host wait until the copy is done, so it is ordered behind the previous replay. It also gives up the overlap.
  • Topic 01 showed the other half of this trade-off: pageable copies block the host (safe but slow), and pinned ones don't (fast, but now you own the synchronization).

Replaying pool-sharing graphs on several streams

Three graphs captured into one pool, replayed concurrently on three streams, write each other's scratch buffers.

Bug, measured with 268,435,456-element (1 GiB) tensors. Every element of y2 and y3 was wrong. The page shows 13, 12, 19; the values depend on timing.

Underneath
  • Each f needs scratch buffers (x**2, 2*x). Captured one after another into one pool, the three graphs were given the same scratch blocks, which is correct only if they run one at a time.
  • On three streams they overlap (each kernel is large enough to run tens of milliseconds), and all three write those blocks at once.
  • The measured values fit that picture: 7 = 1 + 4 + 2 (another graph's 1² next to its own 2·2) and 11 = 4 + 4 + 3 (graph 2's temporaries in graph 3's sum). The addresses weren't logged for this case, so this is consistent arithmetic, not proof.
  • Both fixes left 0 wrong elements out of 268,435,456 per output. Topic 01's rule applies unchanged: streams give permission to overlap, and overlap is only correct when the two sides share no memory.

Diagnosis

Finding the first bad layer

The page's recipe: make execution deterministic, seed identically, clone every layer's output in eager mode and inside the capture, replay, then compare layer by layer and stop at the first difference. Its snippet leaves the model out. Here the model is four Linear + tanh blocks, and block 2 contains the page's "different precision during capture" anti-pattern.

Underneath

Without the bug every layer matches exactly. Replay launches the same kernels on the same data as eager mode, so any non-zero difference is a real behavioral change, not noise. 2.3e-4 is about the size of an FP16 rounding error for values just below 1, which is where tanh outputs live. Note that the clones taken inside the capture are themselves captured kernels: they only hold values after g.replay().

Where torch 2.14 differs from the page

Every difference was traced to a cause. Most of them are recent PyTorch turning a silent failure into a loud one, or into a non-issue.

The replay-order fix is wrong

make_graphed_callables captures all forwards, then the backwards in reverse. The page's "fixed" alternating order still gives 6, 3, 8. Details

Pageable host copies are refused during capture

The freed-CPU-tensor bug and both of its fixes fail at capture instead of returning garbage. torch.full is a graph-safe way to make the tensor on the GPU. Details

Captured pinned blocks are not recycled

Rebuilt with pinned memory, the freed-host-tensor bug did not reproduce: the captured block was withheld from later allocations. Details

Unregistered custom generators still advance

Per-capture generator state is created on first use, so explicit register_generator_state is optional on 2.14. Details

GradScaler step inside the graph fails capture

Its host-side found_inf check is a stream sync, so the page's ❌ variant raises instead of using a stale scale. Details

The autocast-inside fix needs a warmup

Without one, cuBLAS initializes inside the capture and the capture fails with CUBLAS_STATUS_NOT_INITIALIZED. Details

The first five items account for the seven differing cases; the pageable-copy item covers three of them. The sixth is a gap in the page's snippet: with the warmup added, that case matches the page.

Practice

Before you capture

Audit everything that crosses the boundary of the captured region. Most bugs on this page are correct at the capture iteration and wrong only afterwards, so compare against eager mode on several iterations.

Every tensor read from outside

Allocated once, kept alive for the graph's lifetime, updated with copy_ or fill_. Never rebound.

Every Python value

A branch, scalar or shape is a constant of the graph. Make it a device tensor, or keep it outside and capture one graph per case.

Every side effect

Counters, appends, hooks and attribute writes happen once. Move them out, or into a GPU tensor.

Every library launch

It must use torch.cuda.current_stream(), or fork and join with wait_stream. Check in a profiler.

Every output you keep

The next replay overwrites it, and so may any graph that shares the pool. clone() what you keep.

Every host buffer and stream

Wait on an event before rewriting pinned inputs. Never replay pool-sharing graphs concurrently or out of capture order.
